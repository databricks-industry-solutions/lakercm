# Supply-chain pinning stance — read before "fixing" these to hashes.
#
# Every dependency here is exact-pinned (==). The pins, plus CI resolving them
# from one trusted index, are the supply-chain control.
#
# We deliberately do NOT add pip --hash / --require-hashes here:
#   1. Marginal gain. With one trusted index and exact pins,
#      hashes would only guard against the trusted registry serving swapped
#      bytes for an already-pinned version. npm already carries full SRI
#      integrity (package-lock) and the Actions are SHA-pinned; pip is the one
#      ecosystem where hashing costs more than it buys here.
#   2. It breaks the eval path. A single --hash flips the WHOLE file into
#      hash-checking mode, which forces == on every transitive package — and
#      the serverless jobs runtime rejects that against its
#      immutable-package-constraints.txt (see agent_app/requirements-eval.txt).
#      It would also couple the Databricks Apps build to a generated lockfile.
#
# So: version-pinned from a trusted sole registry; artifact hashing is out of
# scope on purpose, not an oversight.
